# RQ2. Resumability 페이로드 직렬화 포맷 & 스키마 버저닝

## 문제

04에서 "Component가 POD라서 직렬화가 단순하다"고 했지만, 구체적 포맷은 미정. 그리고
실제 배포 환경에서 반드시 생기는 문제: **서버가 배포한 HTML에 담긴 직렬화 페이로드**와
**나중에 새로 배포된 client 번들(청크)** 사이에 버전 skew가 생김 (CDN 캐시, 브라우저 tab을
오래 열어둔 사용자 등). Qwik/Astro류가 공통으로 마주치는 문제이고 우리도 예외 아님.

## 하위 질문

1. **포맷**: JSON(디버깅 용이, 크기 큼) vs 컴팩트 바이너리(archetype 테이블 부분 memcpy에
   가까운 형태, 04에서 언급) — 트레이드오프. Rust/WASM 환경이면 바이너리가 자연스럽지만
   백엔드가 언어 무관이어야 하므로(05) 포맷 자체는 언어 무관 스펙으로 고정 필요.
2. **버저닝**: LRef가 참조하는 청크가 이미 재배포로 사라진 경우 어떻게 graceful하게 처리할지
   (Qwik/Next 계열이 흔히 겪는 "stale chunk" 문제 — 보통 해법은 전체 페이지 리로드 강제인데,
   resumability의 핵심 가치(재실행 없음)와 정면충돌)
3. **압축**: Component 스냅샷에 반복 구조(같은 shape의 리스트 아이템들)가 많을 때 압축 전략
4. **Entity id remap** (RQ1 확장 시 등록, 2026-07-22): 스냅샷 안의 Entity 참조(리스트
   keys/rows, LRef captures 등)는 resume 시 새 entity id로의 전역 remap 패스를 요구할
   가능성이 높음 — "archetype 테이블 부분 memcpy 지향"이 실제로는 memcpy+fixup으로
   격하되는 정도를 이 RQ에서 재산정할 것 (RQ1 "검증 필요 (2026-07-22 갱신)" 참고)
5. **dormant 상태의 저장 생존성** (RQ3 잠정 규칙에서 등록, 2026-07-23): dormant island
   (DOM 존재 + LRef 무장 + actor 부재)의 직렬화 상태는 부모 문맥의 재렌더/patch에서
   생존해야 함 — 부모 patch가 island host 내부를 건드리지 않는다는 opaque 경계(RQ3)를
   페이로드 배치가 뒷받침해야 함

## 상태

미착수 — 단, Phase 2 착수(2026-07-23)에서 **잠정 포맷 하나를 실제로 채택**함:
`crates/loom-resume-demo`가 LRef 페이로드를 텍스트 기반
`chunk|symbol|key:value,...`(JSON도 바이너리도 아닌, 파싱에 라이브러리가 필요
없는 가장 단순한 형태)로 `data-loom-lref` 속성에 직접 인코딩하고 실제 브라우저에서
동작을 확인함(roadmap/PHASES.md Phase 2 상태 참고). 이건 하위 질문 1(포맷)에 대한
"이렇게 가정하고 진행한다"는 최소 결정일 뿐, RQ2 자체(JSON vs 바이너리 트레이드오프,
버저닝, 압축, Entity id remap, dormant 저장 생존성)는 여전히 미해결이며 이 데모는
캡처 대상이 스칼라 1개뿐이라 저 하위 질문들이 실제로 부딪히는 지점(리스트/다중
캡처·재배포 버전 skew)을 아직 건드리지 않았다.

**컴파일러 통합 이후(2026-07-24)**: `loom-compiler`가 이 포맷을 직접 생성하도록
일반화하면서 captures가 "스칼라 1개"에서 "컴포넌트가 선언한 `i32` 시그널
전부"(`demo/counter-list.tsx` 기준 여전히 1개뿐이지만, 메커니즘 자체는 N개를
`key:value,key:value`로 comma-join하도록 일반화됨 — `codegen.rs`의
`format_i32_captures`)로 넓어짐. 여전히 안 건드린 것: (1) `StringList` 캡처
(리스트 재개 자체가 별도 항목), (2) 버저닝/재배포 skew — 캡처는 코드젠 시점의
"선언 초기값"만 반영하고 실제 SSR 시점 값이 아니므로(우연히 일치하지만 이유가
다름 — 아래), 소스가 재컴파일되어 시그널 초기값이 바뀌면 이미 배포된 청크와
새 SSR 페이로드 사이의 skew를 어떻게 다룰지는 여전히 미해결. **주의할 정정**:
"캡처값 = 선언 초기값"은 이 데모가 SSR 시점에 시그널을 전혀 변형하지 않기
때문에 우연히 옳게 보일 뿐 — 서버가 요청별로 다른 초기 상태를 렌더링하게 되면
(예: 로그인 사용자별 카운터 시작값) codegen 시점 상수로는 틀린 값이 캡처된다.
이 경우엔 `setup()`이 런타임에 실제 값을 읽어 캡처 문자열을 포맷해야 하는데,
지금 코드젠은 그 경로를 만들지 않았다 — 다음 실측/구현 우선순위로 등록.

**리스트 재개 이후(2026-07-24, 같은 날 후속)**: (1)이 해소됨 — 단, RQ2의
"캡처 페이로드" 하위 질문이 예상한 방향과 다르게 해소됨: `StringList` 상태는
LRef payload에 **전혀 싣지 않는다**. 대신 `DomOps::adopt_children`으로 SSR가
이미 렌더링해 둔 DOM에서 각 row의 현재 값을 직접 읽어온다 — payload 크기가
리스트 길이와 무관하게 O(1)로 유지되는 대신, "캡처=페이로드에 인코딩된 값"이라는
RQ2의 원래 프레이밍 자체를 벗어난 해법이다. 이건 RQ2에 새로 등록할 만한
구조적 통찰: **캡처 페이로드 포맷(JSON/바이너리/텍스트)을 고민하기 전에,
애초에 "무엇을 캡처로 실어야 하는가"부터가 상태 종류에 따라 다르다** — 스칼라는
페이로드에 실어야 하지만(DOM에 그 값이 "존재"하지 않으므로), 리스트/컬렉션류는
이미 DOM 자체가 최신 상태를 들고 있으므로 실을 필요가 없다. 이 구분이 일반화되는지
(예: 조건부의 내부 상태, 중첩 구조)는 미검증. 버저닝/재배포 skew 문제는 여전히
미해결이며, 리스트 쪽은 skew 문제가 아예 없다는 게 흥미로운 부작용(DOM에서
읽으므로 코드젠 시점 상수에 의존하지 않음) — 반면 스칼라 캡처의 skew 문제는
그대로 남아 있다.

**최소 캡처 집합(2026-07-24, 별도 항목)**: 하위 질문 1(포맷)과 별개로, "캡처에
무엇을 담을지"의 최소성 자체는 docs/02가 미해결로 남겨뒀던 질문이었고 현재
IR 범위에서 해소함(`crates/loom-compiler/src/codegen.rs`의
`format_i32_capture_for_action`) — 액션마다 자신이 참조하는 시그널 하나만
캡처. 상세와 스코프 한계는 docs/02·`roadmap/PHASES.md` 참고.

**RQ2 본체 착수(2026-07-24, 같은 날 세 번째 라운드) — 하위 질문 2/4 실측 진행**:

- **하위 질문 2(버저닝/stale chunk) — 부분 해소**: `demo/resume/bootstrap.js`가
  이제 첫 상호작용 시 청크 로드(동적 `import()` + wasm-bindgen init +
  `ResumedComponent` 생성) 어느 단계에서든 실패하면 잡아서 **명확한 진단
  로그를 남기고 전체 페이지를 리로드**한다(Qwik/Next와 동일한 업계 표준
  폴백 — RQ2 문언이 이미 "resumability 핵심 가치(재실행 없음)와 정면충돌"이라고
  지적한 그 트레이드오프를 그대로 받아들인 것, 더 나은 답은 여전히 미해결).
  Playwright로 실제 검증: 존재하지 않는 청크를 참조하는 버튼을 클릭 →
  `import()` 실패 → 콘솔에 원인 로그 → 실제 페이지 네비게이션(리로드) 발생을
  직접 확인(`demo/resume/`에 임시 픽스처 파일로 재현, 검증 후 삭제 — 실제
  데모 파일은 건드리지 않음). **여전히 안 한 것**: (a) 리로드 후에도 사용자가
  "방금 누른 버튼"의 의도(예: count를 1 늘리려던 것)가 사라진다는 UX 손실은
  해소 안 됨 — 그저 무한정 조용히 실패하지 않게 만든 것뿐. (b) 청크 URL에
  버전 해시를 박아 "정확히 어느 배포와 매칭되는 청크인지"를 구분하는 것,
  스키마 버전 필드 자체를 페이로드에 넣는 것 등 진짜 "graceful"(리로드 없이
  복구)에 필요한 인프라는 손대지 않음 — 이번 라운드는 "조용한 실패를 있어보이는
  실패로 바꾼 것"이지 문제 자체를 해소한 게 아님.

- **하위 질문 4(Entity id remap) — 실측 기반 재산정**: 실제로 구현해보니 현재
  스코프(스칼라 + K 기반 리스트)에서는 **remap 패스가 전혀 필요 없다** —
  이유를 실측으로 확인함:
  - 스칼라(`count`): LRef가 시그널 **이름**(`"count"`)만 참조하고, `resume()`은
    `find_node("count")`로 그 이름에 대응하는 DOM 노드를 매번 새로 찾는다.
    직렬화된 페이로드 어디에도 SSR 쪽 `Entity` id가 등장하지 않음 — remap할
    대상 자체가 없음.
  - 리스트(`items`, K 기반): K는 애초에 keyless 설계(RQ1 "재정렬=despawn+
    respawn")라 row identity를 아무도 참조하지 않는다. `adopt_children`이
    DOM 순서대로 새 `Entity`를 스폰하고, 그 매핑은 이 프로세스 안에서만
    산다 — SSR 쪽 `Entity` id는애초에 스냅샷에 실리지도 않았다.
  - **따라서 현재 결론**: "archetype 테이블 부분 memcpy 지향이 실제로는
    memcpy+fixup으로 격하되는 정도"를 재산정하라던 이 하위 질문의 전제 자체가,
    지금 스코프에선 **fixup이 0**이라는 뜻으로 해소됨 — 그러나 이건 "Entity id
    remap이 필요 없다"는 일반 결론이 아니라 **"이름 기반 조회(스칼라) + keyless
    후보(K)를 쓰는 한" 필요 없다**는 조건부 결론이다.
  - **remap이 실제로 필요해지는 지점(구현 안 함, 설계만)**: RQ1의 keyed 후보
    D/E를 resume 대상으로 쓰게 되면 상황이 달라진다 — D는 `RowKey`(row가
    소유한 안정적 키)를, E는 `OrderKey`(entity 자신을 포함하는 전순서 키)를
    쓰는데, 이 키들이 "어느 entity가 어느 논리적 row인지"를 encode하고 있어서,
    캡처 페이로드에 그 키들을 실으려면 **SSR 쪽 Entity id를 어떤 안정적
    식별자로 대체해서 실어야 하고**(Entity 자체는 `bevy_ecs`의 재시작 간
    비영속 handle이라 그대로 못 씀), resume 쪽에서 그 식별자를 **새 Entity id로
    되짚어(remap) OrderKey/RowKey를 재구성**해야 한다 — 이게 바로 이 하위
    질문이 원래 우려하던 fixup 비용이다. E의 `OrderKeyMembers`처럼 entity
    참조 자체를 Component 필드로 들고 있는 구조는 특히 더 손이 많이 감(단순
    치환이 아니라 참조 그래프 전체의 일관된 재작성이 필요). **다음 우선순위**:
    RQ1의 D/E가 resume 대상으로 채택되면(현재는 K만 지원) 이 remap 인프라를
    실제로 설계·구현할 것 — 그 전까지는 조건부로 미착수 상태 유지가 정직한
    서술.

- **하위 질문 3(압축) — 아직 문제가 아님, 판단 유보**: 현재 페이로드는
  스칼라 액션 하나당 `key:value` 최대 1쌍(예: `"count:0"`, 6바이트)이고 리스트
  액션은 아예 빈 문자열이다 — 압축을 고민할 반복 구조 자체가 아직 없음.
  압축이 실제 문제가 되는 지점은 (a) 한 컴포넌트가 여러 개의 독립 `i32`
  시그널을 가져 캡처가 여러 쌍으로 늘어나거나, (b) 리스트 재개가 지금처럼
  "DOM에서 복구"가 아니라 "페이로드에 직접 인코딩"하는 방향으로 바뀌는
  경우(현재는 안 그럼) — 둘 다 아직 실측 대상이 아니므로, 압축 전략 결정은
  그 시점까지 의도적으로 유보함(성급한 최적화 방지).

- **하위 질문 5(dormant island 생존)**: Phase 3(Islands)이 아직 시작 전이라
  여전히 손대지 않음 — 위 remap과 마찬가지로 선행 조건(Island 인프라 자체)이
  없으므로 조건부 미착수.
